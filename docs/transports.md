# Browsers over WebSocket, the desktop app over UDP, in one match

`transport_mode` (default `dual`) makes the server listen twice: WebSocket on TCP `port` for browsers and ENet on UDP `effective_enet_port()` (the same number by default) for native clients, behind one `DotDualPeer` (dot-core's `DotTransportDual`). `websocket` is the behaviour before dual; `enet` is native only. Where the build has no ENet, `dual` is WebSocket with a WARN.

- **One UDP port for ENet, A2S and DQP.** The query protocols answer on the game port by default and ENet cannot share a socket, so when they are on the same number (`enet_shares_query_port()`) the transport's demux owns the port and dot-server-query registers handlers on it (`share_udp_port`) instead of binding. On different numbers ENet binds directly and pays no relay hop.
- **The UDP side binds `effective_enet_bind_address()`**, which follows the query listener's interface. Behind nginx the game's WebSocket is on loopback and nginx cannot carry UDP, so ENet faces the world exactly like the queries. No certificate is involved on that path.
- **Advertised**: `enet_port()` goes out in DQP's info (`enet_port`) and A2S's keywords (`udp:<port>`). The client link tries UDP first on a native build (`transport_preference: auto`) for `udp_connect_timeout_sec` (2.5 s), then falls back to WebSocket. It derives the UDP address from a plain `host:port`; a `ws(s)://` address names a proxy, so only an explicit `udp_address` (the shell's `--udp`) makes it try UDP then.
- **A native WebSocket join to a public bare `host:port` tries `wss://` first** (`_tls_first`), for `tls_connect_timeout_sec` (2.5 s), then plain `ws://`. Every listed server is reached by browsers from an HTTPS page, so its game port is a TLS port, and the address the site hands the desktop app is that port: dialled plain it answered nginx's "400 plain HTTP request sent to HTTPS port", so a desktop player without UDP could not join a server any browser could. Loopback, private and link-local addresses and an explicit scheme go straight to what they say. A wrong guess costs the whole timeout: dot-server's plain listener does not answer a ClientHello.
- **ENet is cleartext, so no bearer secret rides it.** A ticket is safe in the clear (single-use, a minute long, this server only, and bound to this connection: the challenge's `ticket_nonce` is signed into it and the server passes its own copy, `DotClientSession.ticket_nonce`, to dot-auth's `authenticate`, so a copy taken off the wire is refused on any other connection). An access token (`introspect`) or an account password (`local`) is not: on ENet the link sends no credentials at all and rejoins over WebSocket (`_may_send_credential_here`; `signon_revision` asserts nothing arrived over UDP). With `transport_preference: udp` it refuses the join instead. DTLS was the alternative and is the wrong trade: it needs the certificate the native path exists to avoid. A server's own join password is shared, not an account's, and is still sent. `introspect` sends a single-use join token, not the access token, and only to an audience in `first_party_audiences` (the challenge's `join_audience`); otherwise a ticket, else the join fails as `forbidden` (dot-auth `docs/strategies.md`).
- **Peer addresses**: `_address_of` asks the peer's `get_peer_address`, which `DotDualPeer` answers with the real client address behind the demux's relay. A plain ENet server used to log, rate-limit and ban "unknown".

**A host places `DotServer` and `DotClientLink` under its own `MultiplayerAPI` root.** Godot addresses an RPC by the receiver's path relative to that root, so a server at `/root/Host/Server` and a client at `/root/Shell/Server` under the default root answer every call with "Node not found". dot-server-deploy's host and shell each call `get_tree().set_multiplayer(api, <own subtree>)`.
